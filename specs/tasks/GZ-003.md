# GZ-003 需求与项目设计审计及多 Agent 协作交付基线

## 背景

GZ-001 已建立仓库原生 Governance/Harness，GZ-002 已把 Guize V1 的需求、架构、数据、接口、事件、工作流、中间件、状态机、部署、测试和 WBS 收敛为研发设计总基线。

当前仓库已具备单任务的分支、范围、Evidence 和 CI 门禁，但还缺少多 Agent 并行开发需要的任务依赖、路径所有权、共享文件控制、契约输入输出、交接证据、独立审查和集成顺序。与此同时，设计总基线中的若干内容仍停留在规划态，不能直接等同于可并行实现的机器契约。

## 目标

1. 以当前 `main` 为唯一事实基线，审计需求、设计、ADR、机器契约、POC、实现和验收的完整性；
2. 明确哪些内容已冻结、哪些仅是规划、哪些必须先契约化或 POC；
3. 建立“契约波次 → 并行实现波次 → 集成波次”的多 Agent 交付模型；
4. 建立机器可检查的 Coordination Descriptor、路径所有权、依赖 DAG、角色分离和 Handoff Evidence；
5. 建立 Collaboration Gate 和配套测试；
6. 形成后续 GZ-004 及以后任务可直接执行的工作包计划。

## 风险

- 多 Agent 并行不能替代机器契约；在 OpenAPI/Event/DDL/Workflow Contract 冻结前直接并行编码会放大返工。
- 中央协调文件若被所有 Agent 高频修改会形成冲突，因此采用每任务一个 Descriptor，Program Plan 只在编排任务中更新。
- GitHub 分支无法天然实现跨分支文件锁，路径冲突检测依赖先将计划 Descriptor 合并到 `main`。
- POC 未完成前，A380、ATS、700TB、百度云和恢复能力不得转为生产承诺。

## 回滚

PR 合并前直接关闭 PR 并保留分支及 Evidence。若已合并，必须从最新 `main` 创建独立 `fix/GZ-003-...` 分支，通过 Revert PR 回滚新增协作门禁、脚本、模板和文档；禁止直接推送 `main` 或改写历史。
