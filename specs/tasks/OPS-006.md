# OPS-006 建立 fail-closed Program Task Registration 生命周期

## 背景

PR #51 / Issue #50 暴露了一个独立于 POC 内容的治理闭环死锁：普通任务必须先存在于 canonical Program Plan 才能 Reservation，但现有 Task checker、Agent Coordination dispatcher、Task Scope dispatcher 与 lifecycle guards 都不接受 `planned` Task Spec。继续借用已完成的 GZ-003 会违反 completed-task immutable scope，也会把实际治理改动伪装成 Evidence 维护。

OPS-006 建立独立的 `absent → planned` Registration 阶段。Registration 只登记未来任务身份、范围与 DAG 关系，不创建 Active Work Lease，不允许实现，也不代替后续 Reservation。

PR #53 首轮 exact-head CI 还证明 `check-project-readiness.py` 将 W1 中已完成的 GZ-004 永久计入 `maxConcurrent`，导致 GZ-010 与新登记的 planned OPS-006 被误判为三项并发。协议已将 Wave 定义为“允许的最早并行窗口”，而运行期并发由 Reservation/Active Work 单独校验；因此 OPS-006 只允许让 `completed/cancelled` 终态释放 Wave 槽位，其他状态仍继续占用，不提高任何全局或 Wave 上限。

由于当前 Harness 尚不理解 Registration，本任务自身采用一次性、可审计的三阶段自举：Registration PR、Reservation PR、Implementation PR。任何阶段均不得直接推送或合并到 `main`，不得复用 completed Task 身份，也不得引入可重复使用的 bypass。

## 目标

- 定义并机器执行普通 Program Task 的 metadata-only Registration；
- 允许 exactly one 新 Task 从不存在进入 `planned`，同时保持 Registry 与 Completion Ledger 不变；
- 允许对尚未激活的下游 Task 做最小、追加式 DAG 接入，使新 Task 保持在最终发布依赖闭包；
- 将 `planned` 识别为无 Lease、无实现权限的 metadata state；
- 让 `completed/cancelled` 终态历史释放 Wave occupancy，其他非终态仍按原并发上限占位；
- 保持 `planned → reserved → in_progress → review → integration → completed` 既有生命周期不被放宽；
- 为 OPS-005 等后续维护任务提供正式、可重复、fail-closed 的登记入口。

## 非目标

- 不实现 OPS-005 或修改 POC Program / GZ-010；
- 不修改任何业务、生产、部署或实验结果；
- 不允许 Registration 创建 Active Work Lease；
- 不允许在 Registration 中执行实现、修改 Workflow 或改变既有 Task 身份；
- 不重新打开 completed 的 GZ-003/GZ-014；
- 不增加 `maxActiveTasks`、`maxConcurrent`、`maxHighRisk`，不放宽 critical standalone 或路径冲突约束；
- 不增加 skip、continue-on-error、宽泛 allowlist 或 reusable break-glass。

## 风险

- 把 planned 误解释为已保留或可执行；
- 用 Registration 夹带实现文件；
- 为接入最终依赖闭包而改写既有 DAG；
- 允许多个任务在一个 Registration PR 中加入；
- 把终态释放误写成忽略 planned/blocked 等非终态，从而绕过 Wave capacity；
- 为消除 W1 红灯而提高 `maxConcurrent` 或全局并发上限；
- 将 OPS-005、GZ-010 或 PR #51 的内容混入 OPS-006；
- 以自举为名增加永久 bypass；
- 在 exact HEAD 未复核前批准或合并。

## 回滚

Registration 合并前关闭 PR 并删除分支即可，不修改 `main`。若 Registration 经用户批准后合并但尚未 Reservation，则通过独立 Revert PR 删除 OPS-006 Program Task、移除 GZ-020 末尾的 OPS-006 依赖、删除 `specs/tasks/OPS-006.md` 与 `evidence/OPS-006/**`，然后执行完整治理验证。Reservation 或实现已开始后不得直接删除；必须先按独立 lifecycle rollback Task 解除 Lease 并保留历史。
