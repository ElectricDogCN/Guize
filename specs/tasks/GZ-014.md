# GZ-014 收敛项目交付计划并加固多 Agent 协作一致性

## 背景

GZ-003 已建立需求索引、模块所有权、活动任务登记和协作检查，但合并后仍存在多套后续任务定义、开放 Issue 引用不存在路径、公共机器契约写入者不唯一、GZ-003 Task/ADR 状态未收口，以及 GitHub `main` 未保护等缺口。若直接启动多个 Agent，同一 Task ID、契约目录和依赖顺序可能被不同 Agent 解释为不同工作。

## 目标

1. 建立唯一、机器可校验的 `specs/coordination/program-plan.yaml`；
2. 覆盖 GZ-004～GZ-020、POC-001～POC-010 和 M0～M6 的依赖 DAG；
3. 明确 Requirement、Module、Contract Namespace、Task、POC、Acceptance 的追踪关系；
4. 明确公共契约唯一 owner、consumer 与显式 shared writer；
5. 校验波次容量、high/critical 上限、依赖环、输出路径冲突和契约生产/消费；
6. 收口 GZ-003 Task、ADR、重复 PR/Issue 和外部 Branch Protection blocker；
7. 让后续 Agent 只从 Program Plan、Task Spec、Registry 和 Evidence 恢复工作。

## 非目标

- 不冻结具体 OpenAPI、Event Payload、DDL、Workflow 业务内容；
- 不实现 Java、Python、前端、播放器或 Go 业务代码；
- 不执行硬件、存储、AI、网络或恢复 POC；
- 不修改生产环境、Secrets、权限策略或正式数据；
- 不扩大 bootstrap allowlist 绕过 Registry。

## 风险

- Task ID/Issue 重新定义会影响后续 Agent，必须在无其他活动任务时一次收敛；
- Contract ownership 过严会阻塞消费者，过松会允许多写入者，因此区分 owner、consumer 和 shared writer；
- 外部 GitHub 设置不能由仓库提交替代；
- Program Plan 规模较大，必须通过 Schema、实际仓库集成测试和 Review 防止静默截断。

## 回滚

合并前关闭 PR 并保留分支。合并后从 `main` 创建独立 `fix/GZ-014-...` 分支，通过 Revert PR 恢复旧计划、索引和检查器；不得直接推送 `main`。回滚后执行 Coordination、Readiness、Schema、Governance Tests 和 `make verify`。
